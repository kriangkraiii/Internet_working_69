A1 ภาพรวมและสิ่งที่ต้องเตรียม

ใบงาน 28.1.3 ต้นฉบับใช้ Netmiko ต่อเข้า CSR1000v ตัวเดียวใน DEVASC VM ผ่าน SSH ส่ง show แล้วสร้าง Loopback ด้วย send_config_set() โปรเจคนี้ใช้หลักการเดียวกันแต่ขยายเป็น pipeline ครบวงจร:

inventory.yaml ──► Jinja2 templates ──► deploy.py (backup → push → save → diff)
   (source of truth)                          │
                                              ▼
           evidence/*.md ◄── verify.py (19 checks/router) ◄── fault.py (inject → diagnose → recover)

[OK] captures/01_ike_esp.pcap  — scp มาที่ Mac แล้วเปิดด้วย Wireshark
#ลิงก์เหตุการณ์ที่จับDisplay filterสิ่งที่ต้องชี้ในรายงาน
1R1 ↔ R0IKEv1 Main Mode (6 msg) + Quick Mode (3 msg)isakmpMM1–2 เสนอ policy (AES-256/SHA-256/DH14), MM5–6 เข้ารหัสแล้ว, QM สร้าง IPsec SA
2R1 ↔ R0ทราฟฟิก LAN–LAN หลัง tunnel ขึ้นespเห็นแค่ ESP (SPI, sequence) มองไม่เห็น OSPF/ICMP ข้างใน จึงเป็นหลักฐานว่าการเข้ารหัสทำงาน
3R2 ↔ R0PSK mismatchisakmpMM5 ถูกส่งซ้ำ (retransmission) ไม่มี MM6 ตอบกลับ
4SW-MGMT ↔ EXT-MGMTNetmiko SSH session ขณะรัน verify.pytcp.port==22TCP 3-way handshake (SYN, SYN-ACK, ACK) แล้วตามด้วย SSHv2 key exchange
5SW-MGMT ↔ EXT-MGMTSyslog + NetFlow + SNMPv3syslog || cflow || snmpSyslog เป็น plaintext, NetFlow v9 template/data (Decode As UDP 2055 → CFLOW), SNMPv3 ส่วน PDU ถูกเข้ารหัส
ประเด็นที่ควรอธิบายตอน Q&A: OSPF Hello ไม่โผล่บนลิงก์ WAN เพราะอยู่ใน GRE แล้วถูกห่อด้วย ESP ถ้าต้องการโชว์ header ของ OSPF Hello หรือ DBD ให้ใช้ debug ip ospf packet หรือ Embedded Packet Capture บน Tunnel interface (ถ้า image รองรับ) ส่วนบน WAN ถ้าเห็น OSPF แบบ plaintext แปลว่า IPsec ไม่ได้ทำงาน

B2.1 Topology

INC-02 · OSPF MTU Mismatch บน Tunnel12

Inject
fault.py inject mtu: บน R2 ตั้ง ip mtu 1300 ที่ Tunnel12 (R1 ใช้ 1400) แล้ว shut/no shut เพื่อให้ adjacency เริ่มต้นใหม่ พร้อมเปิด debug ip ospf adj
Timeline
Inject [__:__:__] → ค้าง EXSTART [__:__:__] → ตรวจพบ [__:__:__] → แก้ [__:__:__] → FULL [__:__:__]

อาการ

R2-BR1# show ip ospf neighbor
Neighbor ID     Pri   State           Dead Time   Address         Interface
1.1.1.1           0   EXSTART/  -     00:00:17    172.16.12.1     Tunnel12
R2-BR1# OSPF-1 ADJ   Tu12: Nbr 1.1.1.1 has larger interface MTU
R1-HQ#  %OSPF-5-ADJCHG: Process 1, Nbr 2.2.2.2 on Tunnel12 from EXSTART to DOWN, Neighbor Down: Too many retransmissions

การวินิจฉัย

  1. neighbor มีอยู่แต่ไม่ถึง FULL แปลว่า Hello ผ่านแล้ว (ค่า area, timer, auth ตรงกัน) ปัญหาจึงอยู่ที่ขั้นแลก Database Description
  2. สถานะที่ค้างใน EXSTART/EXCHANGE มีสาเหตุหลักคือ MTU mismatch และ router-id ซ้ำ ตรวจ router-id ด้วย show ip protocols แล้วไม่ซ้ำ
  3. show ip interface Tunnel12 | i MTU ทั้งสองฝั่งได้ 1300 กับ 1400 ซึ่งยืนยันได้จาก debug

Root Cause

OSPF ใส่ค่า Interface MTU ไว้ใน DBD packet (RFC 2328 §10.6) ผู้รับจะทิ้ง DBD ที่ระบุ MTU มากกว่า MTU ของตัวเอง R2 (1300) จึงไม่รับ DBD จาก R1 (1400) ทำให้ adjacency วนอยู่ใน EXSTART/EXCHANGE แม้ Hello จะผ่าน สาเหตุต้นทางคือค่า ip mtu สองฝั่งของลิงก์เดียวกันไม่ตรงกัน

การแก้ไข

R2-BR1(config)# interface Tunnel12
R2-BR1(config-if)# ip mtu 1400          → neighbor FULL ภายในไม่กี่วินาที

ทางเลือกที่ไม่แนะนำ: ip ospf mtu-ignore ทำให้ adjacency ขึ้นได้ แต่ซ่อนปัญหาไว้ แพ็กเก็ตขนาดใหญ่จะยังถูก fragment หรือ drop เหมือนเดิม การป้องกัน: กำหนด MTU ใน template เป็นค่ากลางค่าเดียว และ verify.py ตรวจว่า MTU ของ tunnel ทั้งสองฝั่งเท่ากัน

B6 บทเรียนและงานต่อยอด

  • การมี OOB management และ golden config ทำให้กล้ากดรัน fault injection เพราะรู้ว่ากู้คืนได้เสมอ
  • อาการเดียวกัน (OSPF down) มีได้หลายสาเหตุ (PSK, MTU, link) การไล่ตรวจตาม layer และใช้ข้อมูลจากหลายแหล่ง (show, syslog, debug, pcap) ช่วยให้ระบุสาเหตุได้เร็ว
  • ข้อจำกัด: Netmiko เป็น imperative จึงต้องเขียนตัวตรวจ diff และ verify เอง, credential ยังเป็น local user, PSK ยังไม่ใช่ PKI
  • งานต่อยอด: CI pipeline (GitHub Actions) ที่รัน --dry-run และ lint config ทุก commit, TACACS+/RADIUS, IKEv2 + certificate, DMVPN, ทำ dashboard จาก NetFlow, ย้ายไปใช้ IOS-XE และ RESTCONF

ภาคผนวก ก · เตรียมตอบ Technical Q&A

คำถามที่คาดว่าจะถูกถามแนวคำตอบ
ทำไมไม่รัน OSPF บน WAN ด้วยถ้า router เรียนรู้ tunnel destination ผ่าน tunnel เองจะเกิด recursive routing (%TUN-5-RECURDOWN) ทำให้ tunnel ล่มวนซ้ำ จึงใช้ static default route ผ่าน ISP สำหรับ underlay
ทำไม ip mtu 1400 และ adjust-mss 13601500 − GRE 24 − ESP transport overhead (SPI/Seq/IV/pad/ICV ประมาณ 40–60 byte) ≈ 1416 จึงปัดลงเป็น 1400 เพื่อเผื่อไว้ ส่วน MSS = 1400 − IP 20 − TCP 20 = 1360 ช่วยกัน fragmentation
Transport mode กับ Tunnel modeGRE สร้าง outer IP header ที่ปลายทางเดียวกันอยู่แล้ว การใช้ transport mode จึงประหยัด IP header ซ้ำได้ 20 byte
ทำไม OSPF ค้างที่ EXSTART เมื่อ MTU ไม่ตรงกันDBD packet ระบุ interface MTU ไว้ ผู้รับจะปฏิเสธ DBD ที่มี MTU มากกว่าของตัวเอง ทำให้แลก database ไม่สำเร็จ แต่ Hello ไม่ได้ตรวจ MTU จึงยังเห็น neighbor อยู่
รู้ได้อย่างไรว่าเป็น PSK ผิด ไม่ใช่ policy ผิดถ้า policy ไม่ตรงกันจะล้มตั้งแต่ MM1/MM2 (MM_NO_STATE และ “atts are not acceptable”) แต่ PSK ผิดจะผ่าน MM1–4 แล้วล้มที่ MM5/6 ซึ่งเป็นจุดแรกที่ถอดรหัสด้วย key จาก PSK จึงเห็น MM_KEY_EXCH และ IKMP_BAD_MESSAGE
CoPP class Routing ทำไม exceed-action transmitไม่ควร drop routing protocol เพราะจะทำให้ adjacency ล่มเอง จึงใช้ class นี้เพื่อนับและเฝ้าดูเท่านั้น ส่วน ICMP/default จำกัดเข้มเพื่อกัน DoS ไปยัง CPU
Netmiko ต่างจาก Paramiko อย่างไรNetmiko ต่อยอดจาก Paramiko โดยจัดการเรื่อง prompt, paging (terminal length 0), enable/config mode, timing และ TextFSM ให้ตามชนิดอุปกรณ์
send_command กับ send_command_timingแบบแรกรอจนเจอ prompt ตาม pattern ส่วนแบบหลังรอตามเวลา เหมาะกับคำสั่งที่มีคำถามโต้ตอบหรือ prompt เปลี่ยน เช่น clear crypto session
Idempotent ไหม ถ้ารัน deploy ซ้ำIOS CLI เป็น merge จึงรันซ้ำได้โดยไม่เสียหาย และ diff จะเป็นศูนย์ ยกเว้น snmp-server user ที่ไม่แสดงใน running-config ส่วนการลบ config เก่าต้องใช้ configure replace
ทำไม Wireshark บน WAN ไม่เห็น OSPFOSPF อยู่ใน GRE และถูกห่อด้วย ESP จึงเห็นเพียง ESP ซึ่งเป็นหลักฐานว่าการเข้ารหัสทำงาน
SNMPv3 มีระดับความปลอดภัยอะไรบ้างnoAuthNoPriv / authNoPriv / authPriv งานนี้ใช้ authPriv (SHA + AES-128) และจำกัด manager ด้วย ACL
ถ้า branch เพิ่มเป็น 50 แห่งต้องแก้อะไรเพิ่ม entry ใน inventory ได้ทันที แต่ควรเปลี่ยน overlay เป็น DMVPN Phase 3 และใช้ OSPF area แยกหรือ BGP ตาม T2/T3
